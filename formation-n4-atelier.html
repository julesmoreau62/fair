Formation FAIR · Niveau 4 · Atelier pratique

Ma première tâche programmée

Un robot qui rappelle au bureau les échéances du club, chaque matin, sans que personne n'ait à y penser. Vous le copiez depuis le dépôt modèle de FAIR dans un espace au nom du club, vous le lancez en mode essai, vous lisez ce qu'il a fait, et vous savez l'arrêter. Pas une ligne de code à écrire.

Le cas de l'atelier

Le rappel qui n'est jamais venu

Malgré la règle du bureau, Malik avait installé seul, sur son compte GitHub personnel, un robot qui rappelait les échéances du club. Dépôt public, « pour que ce soit gratuit ». Il marchait très bien, jusqu'au départ de Malik. En novembre, le dossier de subvention de la mairie part avec dix jours de retard : le rappel n'est jamais venu.

  • MarsMalik crée le robot sur son compte. Personne d'autre n'y a accès, et le bureau ne sait pas vraiment qu'il existe.
  • JuinMalik part faire ses études dans une autre ville. Plus personne ne modifie le dépôt.
  • Août60 jours sans activité sur un dépôt public : GitHub coupe le robot. L'e-mail qui le signale part chez Malik, qui ne le lit pas.
  • NovembrePas de rappel pour le dossier de la mairie. Le trésorier s'en aperçoit dix jours après la date limite.
  • DécembreLe bureau reprend tout : une organisation au nom du club, deux propriétaires, le modèle FAIR et un robot de garde.

Étape 1 · Les mots

Dépôt, robot,
horaire

GitHub est un service où l'on range des fichiers avec l'historique de chaque modification. GitHub Actions y ajoute des robots qui tournent à heure fixe, sur les ordinateurs de GitHub. L'interface est en anglais : voici les huit mots à connaître, et leur nom à l'écran.

Le motÀ l'écranCe que c'est
Le dépôtRepositoryLe dossier du projet : ses fichiers, et l'historique de chaque modification, avec qui l'a faite.
L'organisationOrganizationL'espace au nom du club, qui possède les dépôts. Les bénévoles y sont invités avec leur propre compte.
Le robotWorkflowUn fichier du dossier .github/workflows : quand il tourne, avec quels droits, et ce qu'il fait.
L'horaireSchedule, cronLa ligne qui dit quand le robot se lance : 17 7 * * *, tous les jours à 7 h 17.
L'exécution et son journalRun, logsChaque passage du robot, avec un résumé et le détail de chaque étape. C'est là qu'on regarde quand quelque chose cloche.
Le ticketIssueUne note dans l'onglet Issues, avec des cases à cocher. Les personnes qui suivent le dépôt reçoivent un e-mail.
La variable et le secretVariables, secretsDes réglages rangés à part : une variable se relit, un secret jamais, pas même par celui qui l'a saisi.
Le modèleTemplateUn dépôt prêt à copier, avec le bouton « Use this template ».

GitHub n'est pas un endroit pour les données des adhérents, même dans un dépôt privé. Les robots de cet atelier n'en touchent aucune : des dates, des rôles, des pages publiques. Ceux qui en ont besoin se construisent dans le tableur du club (voir le catalogue des automatisations).

Étape 2 · Le dépôt du club

Au nom du club,
à deux

La leçon de Malik : un robot vit aussi longtemps que le compte qui le porte. Il se range donc dans une organisation au nom du club, que deux personnes savent administrer. C'est la règle du niveau 4, appliquée à GitHub.

Avant de copier quoi que ce soit

  • Une organisation au nom du club, avec l'offre gratuite, créée avec une adresse e-mail du club
  • Deux propriétaires : le responsable des robots et la personne de secours
  • Un compte personnel par bénévole, invité dans l'organisation : jamais de compte partagé
  • La double authentification activée sur chaque compte
  • Au départ d'un bénévole : accès retiré le jour même, secrets qu'il connaissait changés

Les quatre robots du modèle ne contiennent aucune donnée personnelle : un seul dépôt public leur convient, si vous voulez le site (voir la page d'exemple). Sinon, choisissez le privé. Offres GitHub vérifiées en octobre 2026.

Étape 3 · Pas à pas

Copier,
lancer, lire

Le robot des rappels, du modèle à la première exécution. Comptez une demi-heure, à deux de préférence : le responsable et la personne de secours, chacun sur son compte.

  1. Étape 1

    Copier le modèle

    Sur la page du dépôt modèle, bouton vert « Use this template », puis « Create a new repository ». Propriétaire : l'organisation du club. Nom : par exemple robots-du-club.

  2. Étape 2

    Ouvrir l'onglet Actions

    Les quatre robots y sont listés. Si GitHub le demande, activez-les : ils restent en mode essai.

  3. Étape 3

    Lancer à la main

    « Rappels des obligations », bouton « Run workflow ». Dans la case de la date simulée, tapez 2026-11-06 : sept jours avant le dossier fictif de la mairie.

  4. Étape 4

    Lire le résumé

    Cliquez sur l'exécution. Le résumé affiche les échéances des 60 prochains jours et le ticket qui aurait été ouvert. Le détail est dans l'étape « Préparer les rappels du jour ».

  5. Étape 5

    Mettre les échéances du club

    Dans donnees/obligations.csv, crayon « Edit » : remplacez les lignes d'exemple, avec des rôles, jamais des noms. « Commit changes », puis relancez.

  6. Étape 6

    Passer en réel, après le bureau

    La fiche R.E.L.A.I.S. validée, « Settings », « Secrets and variables », « Actions », onglet « Variables » : MODE_ESSAI = non. Les rappels deviennent des tickets.

Étape 4 · L'horaire

Lire
un cron

La ligne cron dit quand le robot se lance, en cinq champs séparés par des espaces. Une étoile veut dire « tous ». Juste en dessous, la ligne timezone dit à quelle heure on compte.

ChampValeursDans « 17 7 * * 1 »
Minute0 à 5917
Heure0 à 237
Jour du mois1 à 31* : tous
Mois1 à 12* : tous
Jour de la semaine0 (dimanche) à 6 (samedi)1 : le lundi
Dans le fichier du robot
on:
  schedule:
    - cron: "17 7 * * 1"
      timezone: "Europe/Paris"
  workflow_dispatch:

# Chaque lundi à 7 h 17, heure de Paris,
# et un bouton pour le lancer à la main.
Piège · Le fuseau

Sans timezone, l'heure universelle

Sans la ligne timezone, GitHub compte en temps universel : à Paris, le robot passe une heure plus tard en hiver, deux heures plus tard en été.

Piège · L'heure pile

L'embouteillage de 7 h 00

GitHub prévient que les exécutions peuvent être retardées aux heures chargées, surtout en début d'heure. 7 h 17 plutôt que 7 h 00.

Piège · Le dimanche

La semaine commence à 0

0 pour dimanche, 1 pour lundi, 6 pour samedi. « 1-5 » veut dire du lundi au vendredi, « 1,4 » le lundi et le jeudi.

La règle

Pas plus souvent que nécessaire

GitHub n'accepte pas moins de cinq minutes entre deux exécutions, et un club n'en a jamais besoin : une fois par jour suffit presque toujours.

Exercice 1 · Trois horaires

Le bureau veut trois robots. Écrivez la ligne cron de chacun, puis vérifiez avec le corrigé ou avec le traducteur juste en dessous.

La consigne
  1. Écrivez la ligne cron des deux premiers besoins, avec le bon fuseau.
  2. Dites à quelle heure part le troisième robot, en hiver et en été.
Les trois besoins

Le planning des bénévoles : l'alerte des créneaux vides, le jeudi vers 19 h.

Le pointage de la rentrée : chaque nuit vers 2 h, en septembre et en octobre seulement.

Le robot de Malik : cron: "0 18 * * 5", sans ligne timezone.

Voir le corrigé

1. Le planning. "7 19 * * 4" : 19 h 07, le jeudi (4), avec timezone: "Europe/Paris". Pas 19 h 00, l'heure pile est embouteillée.

2. Le pointage. "13 2 * 9,10 *" : 2 h 13, tous les jours de septembre (9) et d'octobre (10), avec le même fuseau.

3. Le robot de Malik part le vendredi à 18 h en temps universel, soit 19 h à Paris en hiver et 20 h en été, avec un éventuel retard à l'heure pile. Correction : "11 18 * * 5" et timezone: "Europe/Paris".

Étape 5 · Relire

        
Ce que l'IA écrit,
on le relit

        
Pour adapter un robot ou en créer un, votre assistant IA écrit le fichier, vite et souvent bien. Mais il lui arrive de donner trop de droits, d'oublier le fuseau ou de proposer d'écrire un mot de passe en clair. Huit points avant d'activer quoi que ce soit. Un seul « non », et le robot reste en mode essai.

      

      
    
        
  1. Les droits au strict nécessaireUn bloc permissions en haut du fichier, et chaque droit sert : issues: write pour ouvrir un ticket, rien de plus.
    2. 
        
  2. Rien de sensible dans le fichierMots de passe, clés et adresses passent par les secrets, et entrent dans les commandes par env:.
    3. 
        
  3. Les outils extérieurs figésChaque ligne uses: pointe vers une empreinte, une longue suite de chiffres et de lettres, pas vers @v7.
    4. 
        
  4. L'heure de Paristimezone: "Europe/Paris", et pas à l'heure pile.
    5. 
        
  5. Le mode essaiTant que le bureau n'a pas validé, rien ne sort du dépôt.
    6. 
        
  6. Un arrêt possibleL'interrupteur ROBOTS_ACTIFS et une durée maximale, timeout-minutes.
    7. 
        
  7. Aucune donnée personnelleLe robot n'en lit ni n'en écrit, et le dépôt n'en contient aucune.
    8.

          Les secrets · 01
          
Variable ou secret ?

          
Ce qui peut se lire va dans une variable : MODE_ESSAI, l'adresse d'un tableau public. Ce qui ouvre une porte va dans un secret : mot de passe de messagerie, clé d'API, liste des adresses e-mail.

        

        

          Les secrets · 02
          
Personne ne les relit

          
Un secret ne s'affiche plus, même pour les propriétaires, et GitHub le masque dans les journaux. On ne le corrige pas : on le remplace.

        

        

          Les secrets · 03
          
Le jeton du robot

          
À chaque exécution, GitHub crée un jeton temporaire qui n'a que les droits du bloc permissions et expire à la fin du travail. C'est lui qui ouvre les tickets : aucun mot de passe à fournir.

        

        

          Les secrets · 04
          
Au départ d'un bénévole

          
On retire son accès, puis on change chaque secret qu'il a pu connaître. Un mot de passe dans un ancien fichier reste dans l'historique : on le change, on ne se contente pas de l'effacer.

Étape 6 · Quand ça casse

        
Le journal,
les alertes, l'arrêt

        
Un robot ne se plaint pas : il se tait. Quatre réflexes pour savoir quand il casse, et l'arrêter en une minute.

      

      

        

          01 · Le journal
          
Ce qu'il a fait, étape par étape

          
Onglet Actions, le robot, puis l'exécution : le résumé en haut, le détail de chaque étape en dessous. Une étape en rouge, et son message dit souvent quoi corriger.

        

        

          02 · Les alertes
          
Qui est prévenu

          
Quand un robot programmé échoue, GitHub prévient la personne qui a modifié sa ligne cron en dernier. Après un départ, le responsable décale l'horaire d'une minute depuis son compte : les alertes lui reviennent.

        

        

          03 · Les 60 jours
          
Le dépôt public qui dort

          
Sur un dépôt public, GitHub coupe les robots programmés après 60 jours sans activité. Le robot de garde prévient à 45 jours : une mise à jour d'un tableau suffit.

        

        

          04 · L'arrêt
          
En une minute

          
Un robot : onglet Actions, « Disable workflow ». Tous : la variable ROBOTS_ACTIFS à « non ». Les deux propriétaires savent le faire.

        

      

      
Le robot de garde du modèle vérifie chaque lundi que les autres tournent. Il ne peut pas se surveiller lui-même : la première ligne du calendrier des obligations demande une vérification humaine, le 1er de chaque mois.

            Le rappel qui n'est jamais venu
            
Un robot sur le compte personnel de Malik, dans un dépôt public. Malik part en juin, le dépôt ne bouge plus, GitHub coupe le robot en août et prévient Malik. En novembre, le dossier de la mairie part avec dix jours de retard.

          

          

            Voir le corrigé
            

              
1. Le Suivi et l'Incident. Ni responsable désigné par le bureau, ni personne de secours, ni revue : le Suivi n'existait pas. Et l'Incident n'était pas prévu : l'alerte partait chez Malik, et personne ne savait relancer le robot. La règle du niveau 4, « rien sur un compte personnel », n'avait pas été tenue.

              
2. Trois choses l'auraient signalé. Un robot de garde, qui aurait ouvert un ticket dès septembre. La vérification humaine du 1er du mois. Et un dépôt privé, où la règle des 60 jours ne s'applique pas.

              
3. Dans l'ordre

              
    
                
  • Déposer le dossier quand même et prendre contact avec la mairie.

  • Créer l'organisation du club, avec deux propriétaires.
    • 
                
  • Copier le modèle et y reprendre le tableau des obligations de Malik.
    • 
                
  • Écrire la fiche R.E.L.A.I.S., la faire valider, l'inscrire au registre.
